# ADR-0009: проверка действительно нового Instagram-диалога

Дата: 28 сентября 2026 года. Статус: реализовано локально; production outbound выключен.

## Контекст

Первоначальный Instagram MVP считал первым сообщением первый DM, попавший в Lead Hub.
Уже существовавший в Instagram диалог с ручными ответами менеджера получил
автоматическое приветствие. Временной rollout cutoff ограничивал дату DM, но не
возраст Instagram-переписки. Владелец подтвердил, что автоответ допустим только
для первого обращения в действительно новой, ещё не обработанной человеком
переписке.

## Решение

1. Существующий Meta webhook и Lead Hub остаются единственным ingress и источником
   истины для принятого лида. Проверка истории не блокирует сохранение лида,
   сообщения и человеческой Telegram-карточки.
2. При первом DM для нового lead сервис через Instagram Login read-only API ищет
   беседу по Instagram-scoped sender ID и запрашивает до двух последних сообщений.
   Автоответ можно поставить в durable outbox только когда API вернул одну
   беседу и ровно одно сообщение с тем же provider message ID и sender ID.
   Старый диалог, другое сообщение, неполный ответ, HTTP-ошибка или timeout
   означают отказ от автоматического ответа. Сохраняется audit reason.
3. Перед фактическим POST отправитель повторяет эту проверку. Новое сообщение или
   ручной ответ между постановкой и отправкой прекращает отправку. Дополнительно
   проверяется, что лид в Lead Hub остаётся `new` без `firstResponseAt`.
   Подавленное задание переводится в dead-letter с Telegram escalation. Запросы используют только
   фиксированный `graph.instagram.com`, без динамических URL или Ads-токена.
4. Задания прежней версии без исходного provider message ID не отправляются при
   повторном включении. Их нужно отдельно просмотреть; база и outbox не очищаются.
5. `INSTAGRAM_MESSAGING_ENABLED=false` остаётся в production до canary на новом
   диалоге. Включение — отдельный rollout с проверкой backlog и новым cutoff.

## Ограничения

Проверка и отправка не могут быть одной транзакцией с Meta: менеджер теоретически
может ответить в коротком промежутке после последней проверки. Это остаточный
риск; полностью исключить его без механизма владения перепиской у провайдера
нельзя. Если Meta не возвращает нужную историю или она неполна, бот молчит и
работу продолжает человек. Повторные обращения в старых диалогах остаются
ручными. Содержимое переписки и клиентские ID не попадают в логи проверки.

Read-only probe 28 сентября подтвердил в текущей конфигурации ответы lookup по
`user_id` и сообщения с `id`/`from`. ID беседы оказался непрозрачной строкой,
не числом; локальная проверка принимает только безопасный path-segment без
публикации самого ID. Probe не проверяет отправку или доступность всех клиентов.
